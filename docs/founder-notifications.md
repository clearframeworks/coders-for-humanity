# CFH founder notifications

A saved CFH profile creates a durable `profile.created` event in the same database transaction. Shared Auth account creation alone is not a CFH membership event. Public profiles include their chosen display name and profile link; private profiles produce an anonymous notice. Updates do not repeat the signup notice.

The operator installs one trusted founder UUID and verified delivery email in `cfh_private.founder_notification_settings`. This table is inaccessible to browser roles, and no email address, handle or user-editable metadata grants founder authority. The founder needs a CFH profile before this configuration can be saved. Configuration also routes events captured before setup, once each, to the founder's private `/inbox` and the CFH email outbox. Existing profiles predating this migration are not backfilled.

The mail worker is implemented at `/api/internal/founder-notifications` (GET for schedulers, POST for operator tooling). It accepts only a bearer secret of at least 32 characters and refuses to claim work unless delivery is explicitly enabled and all server configuration exists. It leases one event per invocation through database functions granted only to `cfh_notification_worker`; ordinary users cannot invoke those functions or view the queue. The worker role is NOLOGIN and NOINHERIT, has schema usage and execute permission on only the two dispatch functions, and is granted to PostgREST's `authenticator` so a verified scoped JWT can select it. Use these variables:

- `CFH_NOTIFICATION_CRON_SECRET`: request bearer secret, at least 32 characters.
- `CFH_NOTIFICATION_WORKER_JWT`: short-lived server-only JWT issued through trusted operator infrastructure, with role `cfh_notification_worker`. Do not put the shared service-role key or any JWT signing secret in this app. Provision and rotate the scoped token before it expires; expiration causes dispatch to fail closed without silently switching credentials. The issuer must use a signing method accepted by this Supabase project's API.
- `CFH_NOTIFICATION_SENDER_EMAIL`: verified sender address approved for this platform. It is frozen in the outbox on the first send so configuration changes cannot change retry payloads.
- `CFH_NOTIFICATION_RESEND_API_KEY`: sending-only credential approved for that sender's domain.
- `CFH_EMAIL_NOTIFICATIONS_ENABLED=true`: explicit delivery activation. Unset/false disables dispatch.
- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: the existing approved public API configuration. The worker adds its scoped JWT in the Authorization header separately.

The approved recipient is frozen in the outbox at event routing, so retries preserve the identical payload. Every attempt uses `cfh-profile-<event outbox UUID>` as the Resend idempotency key. An abandoned lease expires after two minutes. Retries back off up to one hour, stop after 12 attempts or 20 hours (inside the provider's idempotency window), and permanent provider errors enter `needs_review`. A successful provider receipt is required to mark `sent`; this means provider acceptance, not proven inbox delivery. Never reset uncertain events after that window without checking the provider receipt first.

No scheduler, recipient, credential or delivery activation is installed by these files. After the shared database is healthy, apply the reviewed CFH migration, confirm schema exposure/grants, install the verified founder configuration, configure the server environment, and schedule an authenticated request once a minute. A Vercel Cron job would require the provider's `CRON_SECRET` contract or a scheduler that supports the custom Authorization header; do not simply add a Vercel cron entry without that adjustment. Validate a controlled owner's event and its actual inbox delivery before calling email live. Monitor `requires_sender`, `pending`, `inflight`, and `needs_review` counts privately; no public endpoint exposes recipients or queue details.

This implementation does not change the older central signup mailer, shared Auth/SMTP settings, EVE/EVAN roles, or production runtime flags. Local database and mocked transport tests exercise permissions, private-profile anonymity, rollback, duplicate suppression, leasing, receipt handling, retry backoff and retry expiry. No real mail is sent by these tests.
